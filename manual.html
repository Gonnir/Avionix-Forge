User Manual

Everything the editor does,
and how to actually get MAVLink connected.

A complete walkthrough of every panel in the editor, plus the full field-tested MAVLink setup and troubleshooting guide — wiring, baud rate gotchas, stream rates, and the diagnostic steps that actually isolate a problem.

Red — no MAVLink data received
Green — receiving valid telemetry

01 Quick Start

  1. Pick your board and display in Hardware Setup (top bar).
  2. Drag instruments from the left palette onto the canvas, and give each one a MAVLink Source in the Properties panel.
  3. Wire your flight controller's telemetry port to your board — see MAVLink Setup.
  4. Click Export .ino, open it in Arduino IDE, install the required libraries, compile, and flash.
  5. Watch the status LED. If it stays red, jump to Troubleshooting.

04 Palette & Canvas

Every instrument on the canvas is a live, interactive object.

  • Add: drag an instrument from the left palette onto the canvas.
  • Select: click an instrument. Its properties appear on the right.
  • Move: drag the instrument body.
  • Resize: drag a corner handle.
  • Delete: select it, press Delete/Backspace.
  • Deselect: press Escape, or click empty canvas.
Tip
The canvas is rendered to-scale and in the correct color mode (mono panels render as true black/white, not just grayscale) — what you see is what your physical screen will show.

07 MAVLink Setup

This is the section most worth reading carefully — nearly every real-world connection problem traces back to one of the items below.

Wiring

  • FC TX → board RX, FC RX → board TX — crossed, not straight-through. Wiring TX-to-TX produces the exact same "nothing received" symptom as everything else being wrong.
  • Connect a common ground between the FC and your board if they aren't already sharing one through a common power rail.
  • Double-check the RX/TX pin numbers in Hardware Setup correspond to a valid UART pin pair for the UART peripheral you selected.

Baud rate — the most common single point of failure

The baud rate in Hardware Setup must exactly match the flight controller's configured telemetry baud rate.

ArduPilot-specific gotcha
SERIALx_BAUD is a code, not the literal value. To get 57600 baud, the parameter must be 57, not 57600. Typing the full number directly is one of the most common ArduPilot configuration mistakes.

Fully power-cycle the FC. A parameter "write" alone doesn't guarantee the running firmware has picked up the change.

Protocol selection

Set SERIALx_PROTOCOL to 1 (MAVLink1) or 2 (MAVLink2) on whichever port you've wired to. Any other value means that port sends no MAVLink data at all, regardless of correct wiring or baud.

CRSF — an alternative to MAVLink entirely

Telemetry Protocol in Hardware Setup offers a second option besides MAVLink: CRSF (Crossfire/ExpressLRS) — not a MAVLink variant, but a completely different protocol read directly from an ExpressLRS/Crossfire receiver, the same telemetry stream an EdgeTX radio displays. Selecting it changes what you wire to: the receiver's telemetry pin, not the flight controller's MAVLink port. Baud is fixed at 420000 (the field disappears — nothing to set). Both protocols feed the exact same internal data, so every instrument works identically regardless of which is selected — except RC channel sources, which need MAVLink specifically, since CRSF's telemetry stream doesn't carry RC input data (it flows radio→FC, the opposite direction).

Stream rates — controls how often data updates, not whether it arrives

Easy to overlook because it has nothing to do with wiring, baud, or the generated code — it's purely an FC-side setting. A low value produces a symptom that looks exactly like a rendering problem: gauges appear to update in slow motion even though the display itself is redrawing at full frame rate.

ParameterCoversRecommended

Smooth in demo mode, choppy the instant real telemetry connects → check stream rates before suspecting the board, wiring, or generated code. A perfectly fast rendering pipeline fed by 1Hz source data will always look like it updates once a second, because it does.

Recommended baseline configuration

Going above 115200 baud rarely helps and can hurt — it increases how much data a single CPU core has to parse and decode per second, competing with display-push work for CPU time.

iNav compatibility

iNav's MAVLink telemetry is transmit-only, which is exactly what this tool needs. iNav deliberately maps its own flight modes onto the same HEARTBEAT.custom_mode numbering ArduPilot uses (APM_PLANE_MODE for fixed-wing, APM_COPTER_MODE for multirotor) — so the Flight Mode instrument works correctly with iNav out of the box. One difference: iNav's RSSI uses the same 0–254 raw scale as ArduPilot, not 0–100%.

Double buffering ("ping-pong")

On RP2040, if two full framebuffers fit in RAM, the tool automatically double-buffers: core0 draws the next frame while core1 pushes the previous one, so a frame costs max(render, transfer) instead of render + transfer. RP2040-only — other boards fall back to a single-buffer synchronous push.

Expected frame rates

Targets ~30fps for color panels, ~10fps for mono panels. If actual frame rate is well below this:

  1. Check whether it's a data problem, not rendering — see Stream Rates. This is the most common cause.
  2. If genuinely a rendering bottleneck, time drawAll() and the push block separately — see the diagnostic approach below.

09 Troubleshooting

Status LED meanings

LED stateMeaning
Steady redNo valid MAVLink message received in the last 3 seconds

The standalone diagnostic sketch

Before assuming a bug in the generated code, isolate the connection with a minimal sketch that dumps raw bytes — no display code involved at all:

#define MAVLINK_SERIAL   Serial1
#define MAVLINK_BAUD     57600   // match your FC's SERIALx_BAUD
#define MAVLINK_RX_PIN   1
#define MAVLINK_TX_PIN   0

void setup() {
  Serial.begin(115200);
  delay(2000);
  MAVLINK_SERIAL.setRX(MAVLINK_RX_PIN);
  MAVLINK_SERIAL.setTX(MAVLINK_TX_PIN);
  MAVLINK_SERIAL.begin(MAVLINK_BAUD);
}

void loop() {
  while (MAVLINK_SERIAL.available()) {
    uint8_t b = MAVLINK_SERIAL.read();
    if (b < 0x10) Serial.print('0');
    Serial.print(b, HEX); Serial.print(' ');
    if (b == 0xFE) Serial.print("<-MAVLink1 ");
    if (b == 0xFD) Serial.print("<-MAVLink2 ");
  }
}
What you seeWhat it means
Always 0 bytesNothing reaching the RX pin — wiring, baud, or FC-side protocol/port config
Garbled bytes, no clean markersBytes arriving, but baud mismatch — check the ArduPilot code gotcha
Clean, regular 0xFE/0xFD packetsRaw connection works — a further problem is in the full sketch, not the wire

Decision tree for "stuck in demo mode"

  1. Run the diagnostic sketch with your exact current wiring. Clean data → physical link is fine, skip to step 3.
  2. Garbage or nothing → recheck wiring polarity, the baud code gotcha, SERIALx_PROTOCOL, and power-cycle the FC after any parameter change.
  3. Diagnostic clean but full sketch still red → confirm you're testing a freshly regenerated and reflashed build, not a stale export.
  4. Works on one panel type but not another on the same board → suspect clock/timing ordering issues specific to hardware-SPI color panels, which mono/I2C panels don't share.

10 Telemetry Control

The top bar's telemetry indicator is now a real button, not a static label — it starts and stops the editor's own animated preview.

Click to toggle between the two states shown above.

Useful for holding instruments still while fine-tuning a layout, or comparing two states side by side. This only affects the editor's simulated demo data — it has nothing to do with real hardware MAVLink connectivity, which is a separate, board-side concern (see MAVLink Setup).

Editing still works while paused
Properties, resizing, and adding instruments all work normally while paused — the canvas repaints using whatever values were last live, it just doesn't advance them further until you resume.

11 Instrument Rotation

Rotation is a plain 0° / 90° / 180° / 270° selector, not a free-form angle — and for good reason.

This is a hardware constraint, not an editor limitation: Adafruit GFX and U8g2 have no built-in support for rotating arbitrary drawn content at non-90°-multiple angles without a full software rasterizer, so anything finer wouldn't actually work once compiled — even if a live preview could show it happily.

Support varies by instrument. Rather than leave in a control that would silently do nothing on real hardware, it's simply hidden for types where rotation genuinely has no effect:

CategoryInstrumentsRotation
Circular/dial gaugesArtificial Horizon, Turn Coordinator, Compass, Altimeter Dial, VSI, Arc Gauge, generic Dial, Groundspeed Dial, Home ArrowFully supported
Shape primitivesRectangle, Circle, Oval, Screw HeadFully supported — genuine rotated-polygon math
Indicator lampIndicatorControl hidden — a filled lamp has no directional content to rotate
Linear/rectangularTape family, Mode Indicator, Bar Gauge, Text Value, Home Distance, Static TextControl hidden — needs a render-to-buffer-then-blit system, not a simple angle offset
One exception
The Background Template image gets a full unrestricted 0–359° rotation — it's editor-only and never has to be drawn by real hardware, so the usual constraint doesn't apply.

12 Transparent Colors

Setting any color field to transparent now genuinely skips that draw call — across every instrument, every color-configurable part.

This was audited comprehensively across borders, ticks, needles, hubs, labels, and fills. Previously, "transparent" silently resolved to the instrument's own background color instead of skipping the draw entirely — harmless-looking on a simple solid background, but capable of visibly painting over content underneath on overlapping or layered instrument designs.

The dashed swatch above is "transparent" — selecting it now means nothing gets drawn there, not "drawn in whatever the background happens to be."

14 New Instruments & Options

VSI Tape

Vertical speed shown as a scrolling tape instead of a radial dial — shares the same rendering (and every option: mirroring, tick color, label step) as the other vertical tapes. Defaults to VFR_HUD.climb, range ±10 m/s.

Static Text

A purely decorative text label with no MAVLink source at all — type whatever you want. Configurable text/background/border color, alignment, and size like any other instrument. No rotation control (see the table in Instrument Rotation).

Tape instrument options

OptionApplies toWhat it does
MirroredVertical tapes (not Heading Tape)Flips the layout left-to-right — ticks/pointer move left, value box moves right. Text stays upright and in normal reading order, only its anchor/alignment flips.
Label StepAll tapesManual control over which values get a text label (every 5, every 25, etc.) instead of fully automatic. Heading Tape's version is in degrees (30° default).
Tick Length + Y OffsetHeading TapeIndependent length/position control for major and minor ticks.

Bar Gauge orientation

Now supports vertical fill (bottom-to-top, like a thermometer) in addition to horizontal. Not a rotated version of the horizontal layout — label and value stay upright and readable in both orientations, with ticks, track, and bar redesigned around whichever direction you pick. Set via Orientation in Sizing & Geometry.

Heading Arc

The same scrolling ±45° heading window as Heading Tape, curved along an arc instead of laid out on a straight line — like the compass arc on a real PFD. Arc Sweep (°) controls how tightly it curves; Flipped bends it the other way (frown instead of smile) for mounting at the bottom of a panel instead of the top. A higher heading value always moves the tick to the right, regardless of which way it's bent.

Stick Position

An RC transmitter stick indicator — a square box with a circle that moves inside it, tracking two independent channels for left/right and up/down. Each axis has its own Reverse checkbox (a channel's physical stick direction doesn't always match its raw PWM direction), and Circle Size controls how large the moving dot is relative to the box. Four independently selectable colors: square fill, square border, circle fill, circle border.

RC Channels as a data source

RC Channel 1 through 16 are selectable wherever a MAVLink source dropdown appears, reading raw PWM values (typically ~1000–2000µs) from MAVLink's RC_CHANNELS message. Useful for a threshold-based Indicator lamp watching a switch position, a Text Value showing a raw reading, or driving Stick Position directly. Requires MAVLink mode — CRSF's telemetry stream doesn't carry RC input data (see Protocol).

Unit of Measure

Groundspeed Tape, Airspeed Tape, Altimeter Tape, and VSI/VSI Tape have a Unit of Measure dropdown above their MAVLink Source — a shortcut on top of the existing Multiply By transform, not a separate mechanism. Speed instruments offer m/s, km/h, mph, knots; Altimeter offers meters/feet; VSI offers m/s, ft/min, ft/s. Home Distance has its own selector: Auto (meters, switching to km past 1000m) or fixed meters/km/feet/miles. Groundspeed Dial and Altimeter Dial don't have this dropdown, since their scale/tick-step fields are themselves expressed directly in a fixed unit, not just the displayed value.

Locking any instrument

Any instrument can be locked (Position & Size section) — a locked instrument can't be clicked or dragged on the canvas, protecting it from accidental bumps, but stays fully selectable and editable through the instruments list popup. Purely an editor convenience with no effect on the generated code. Previously only available on Background Template images (see Background Templates); now universal.

Canvas panning and view toggles

The editor viewport can be panned by clicking and dragging empty background at any zoom level. Two toggle buttons next to the zoom controls: show/hide overhangs (whether instrument parts past the screen edge are visible or clipped — useful for previewing exactly what real hardware will show) and show/hide selection box (the dashed outline/glow/label around a selected instrument — the resize handles stay usable either way, only the visual overlay toggles, useful when it's obscuring a small instrument's true edges).

Movement snapping

Dragging an instrument moves it freely by default, including off the edge of the screen for intentional overhangs. Hold Ctrl (Cmd on Mac) while dragging to snap it back to staying fully within the screen bounds.

ST7796S uses a different display library

Every other color panel in this tool is driven by an Adafruit display library. ST7796S (320×480) is the one exception — it uses Arduino_GFX_Library (moononournation) instead, confirmed working through real hardware testing on RP2040 + ST7796S. It presents the same drawing API, so every instrument's generated code looks identical either way. Install it first: Library Manager → search "GFX Library for Arduino". A full 16-bit framebuffer at this resolution would need ~300KB — more than an RP2040's 264KB of SRAM — so double buffering here uses Arduino_Canvas_Indexed instead, an 8-bit buffered canvas (~150KB, fits comfortably). You still draw with normal RGB565 colors exactly like every other panel; the canvas builds its own 256-color palette automatically and only reduces precision if a design genuinely exceeds that, which a typical instrument cluster's limited palette is unlikely to do.

15 Blackbox Log Playback & Video Export

Play a real recorded flight log through the instrument cluster instead of simulated data — useful for reviewing exactly how a design looks with actual flight data, no hardware required.

Loading a log

Click the waveform icon next to the telemetry toggle to load a CSV export of a flight log (Mission Planner's log-to-CSV export is directly supported). A mapping dialog lists every column: pick which one represents elapsed time, and map any columns to a MAVLink source using the same list every instrument's Data Source dropdown uses. Columns matching common ArduPilot/Mission Planner naming (ATT_Roll, GPS_Lat, BAT_Volt, RCIN_C1–C16, and more) are auto-mapped as a starting point.

How playback works

Values are linearly interpolated between the log rows surrounding the current position, so it moves smoothly regardless of the log's actual sample rate. Real multi-message-type exports log each field on only a fraction of rows (GPS at 5% of rows isn't unusual), so sparse columns are automatically forward-filled at load time — each field holds its last known value until the next real reading. Millisecond/microsecond time columns are auto-detected by name and scaled to seconds.

Playback controls

ControlWhat it does
RestartJumps to the beginning, immediately showing the first row's values even while paused.
Play/PauseStarts or stops advancing playback.
Seek sliderLive position during playback; drag to scrub anywhere in the log with instruments updating in real time. Pauses automatically during a drag, resumes after if it was playing.
Unload (✕)Returns to simulated telemetry.

Video export

With a log loaded, the video-camera icon opens an export dialog (frame rate, bitrate). Renders the entire log through the instrument cluster and encodes directly to .webm — not a real-time screen recording, so export is much faster than the log's own duration. Runs entirely in-browser; nothing is uploaded. Requires WebCodecs support (Chrome/Edge).

16 Known Limitations

STM32 custom pin remapping

Not fully implemented — varies too much by board variant. Works fine on STM32's default SPI/I2C pins; genuinely custom pins need board-specific SPI.setMOSI()/setMISO()/setSCLK()/setSSEL() calls added yourself.

RC RSSI scale

RC_CHANNELS.rssi is a device-dependent raw value (0–254), not 0–100%, per the MAVLink spec — true for both ArduPilot and iNav.

Engine RPM

EFI.rpm isn't part of the MAVLink common dialect and isn't decoded — always 0 unless you add a custom MAVLINK_MSG_ID_RPM decoder.

Flight mode numbering is vehicle-specific

HEARTBEAT.custom_mode numbering is entirely firmware- and vehicle-defined. ArduCopter, ArduPlane, Rover, and PX4 all differ. iNav mirrors ArduPilot's numbering, so no changes needed there.

Home position is approximated

No dedicated HOME_POSITION/GPS_GLOBAL_ORIGIN decode — "home" is your first valid GPS fix after boot, not a precise read of the FC's configured home point.
